## 2. Transport Decision (Settling Messenger Open Question #4)

- **What Messenger actually recommends vs brief paraphrase:** `business:docs/submissions/messenger/open-questions.md:36-38` and `DELIVERY_ROADMAP.md:25,28` recommend a **FastAPI WebSocket bound to the B0 verified principal** (JWT → short-lived same-origin session), whereas `briefs/1b-revise.md:42` loosely paraphrased it as *"cookie-authenticated FastAPI WebSocket until B0 identity exists"*. Allowing live multi-user chat on the anonymous `dubaiio_lab_session` cookie (`apps/api/app/actions.py:386-393`) would violate Gate S (`docs/submissions/CLAUDE.md:62`) and owner isolation.
- **Why Browser Supabase Realtime is rejected:**
  1. `supabase/migrations/20261021000100_backend.sql:5-7,32-36` revokes `ALL` on schema `dubaiio` from `PUBLIC, anon, authenticated, service_role`.
  2. Exposing PostgREST/Realtime policies requires `supabase/migrations/` changes, which are forbidden by `docs/submissions/CLAUDE.md:51`.
  3. Local dev/CI runs on SQLite (`DATABASE_URL` blank, `docs/status.md:37`), where Supabase Realtime cannot be tested.
- **P2 Settlement (`SHARED_MEMORY_CROSS_APP_CONTRACT.md` §2.3):** Lock **FastAPI WebSocket on `app.messenger.server:app` (`:8070`)** bound to **B0 verified `user_id` (Gate S)** via a short-lived HttpOnly same-origin session cookie (`cs_session_messenger`) or single-use 60s `Origin`-bound WS ticket (`POST /api/identity/ws-ticket`). FastAPI rechecks `assert_session_active` and `mg_memberships` on handshake, subscribe, send, and replay, and drops sockets immediately on revoke. Before Gate S, Messenger UI operates in labelled `Demo data` fixture mode only.
- **Narrow Ops Sub-Question for Founder Gate (non-blocking for P2/B0/local `MG-B2`):** Confirm the manual/scripted procedure for applying `apps/messenger/supabase/` and `apps/community/supabase/` RLS SQL to hosted staging Postgres before live Postgres pilot traffic.
