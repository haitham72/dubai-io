## 0. Founder requirement — do not omit

Populate the *actual working Community feed* with **10 distinct synthetic social-media users**, their profiles, posts, comments, reactions, connections, communities, and time-ordered activity. An orchestrating IDE agent must inspect the existing repository and then **delegate separate work packages to subagents** (or independently tracked equivalent tasks if true subagent dispatch is unavailable). This is **an executable demo-data + functionality test plan**, not ten fake UI cards and not a request to create ten real human accounts.

The aim is to demonstrate a Facebook-like product with a believable, functioning social graph and enough content to test Community's ranking, moderation, notifications, and consented personal-memory features. **AI personas are test fixtures.** They must never impersonate real residents, acquire real contacts, contact outsiders, manipulate public engagement, or be presented as authentic users.

## 2. Minimum dataset and realistic network

Create a **14-day, timestamped** simulation (`Asia/Dubai` local display, UTC storage), with reproducible randomness (`seed=20261126` or equivalent). Populate through the real app's domain service/API or a controlled, idempotent development seed adapter — not hard-coded rendered posts.

| Entity / behavior | Minimum acceptance target |
|---|---|
| Distinct synthetic accounts | Exactly **10**, stable identifiers and independent owners |
| Public communities | **7** (listed in §1), member lists and appropriate permissions |
| Original posts | **40 total**, at least 3 per user and at least 1 image post per 3 users |
| Comments and nested replies | **90 total**, at least 15 actual parent-child reply chains |
| Reactions | **120 total**, distributed across users and posts |
| Follow / friend edges | **20** intentional directed follow edges, no impossible self-follows |
| Community memberships | At least **20**, with each user joining ≥ 2 groups |
| Notifications | At least **20** generated by actual interactions, correct recipient |
| Saved/bookmarked posts | At least **10** distinct owner-scoped saves |
| Moderation test cases | 2 labeled fixtures (one harmless false-positive candidate, one clear spam), not real abusive content |

No actor should write all posts in a single minute. Vary author activity and timing; ensure a mix of unanswered questions, thoughtful answers, project updates, images, invitations, discussions, and ordinary casual posts. Use **no invented provider ratings, prices, operating hours, civic laws, event tickets, or purported current news**. A location reference may be an example discussion topic, not verified advice. Keep interactions semantically coherent: comments address the parent post and conversations evolve over time.

Use model generation only where useful to draft seed content; deterministic validation, not an LLM, governs mutations. If the IDE does not have subagent tools, the orchestrator must explicitly note that limitation and produce the same work packages as queued tasks. Do not claim to have delegated work when no child tasks were actually launched.

## 5. Lifecycle of one persona and data flows

1. Build a deterministic `sim-xx` owner and public profile under the **demo-only** namespace `community-demo-10-v1`.
2. Join assigned communities; follow plausible related actors; establish graph edges through server validation.
3. Publish a dated seed post through the app's post service; store provenance `{kind: demo_fixture, actor_id, seed_run_id, timestamp}`.
4. Other persona actors reply, react, bookmark and trigger recipient-scoped notifications through the genuine backend event path.
5. A normal test viewer logs in and sees Following/Communities/Discover feeds; pagination and rankings operate over persisted fixture records.
6. Consent-gated memory integration: test viewer can explicitly save a topic preference. **Synthetic actor posts and private conversations must not become verified facts about real users.**
7. Run replay twice to prove idempotency; run scoped teardown to remove only `community-demo-10-v1` records while preserving unrelated data.

## 6. Safety, privacy, and environment boundaries

- Never seed production, real public groups or outsiders without explicit approval and a clearly labeled synthetic-demo environment. Default to `--dry-run` and local/test Supabase project.
- Require an environment guard (`DEMO_SEED_ENABLED=true`, non-production target, explicit `--apply`) and a stable namespace; fail closed if verification fails.
- Do not bypass RLS or server owner checks in normal APIs. A privileged internal fixture installer, if necessary, must be isolated from public endpoints, logged, and restricted to demo environments.
- No direct messages to real users, no fake endorsements, bought followers, fabricated reviews, scraped real profiles, or generated images of actual private people.
- Seeded activity is `demo_fixture`, excluded from public metrics, ranking-training signals, conversion metrics and user-specific long-term memory by default.
- All content is editable/removable via controlled demo tools. Test reset after a crash must be safe and idempotent.

## 7. Automated acceptance tests (must be green)

- [ ] Exactly ten synthetic users and seven groups exist, and all target counts in §2 are verified with database/API queries.
- [ ] Every item has correct `actor_id`, owner, timestamp, provenance and stable idempotency key.
- [ ] Comments, reactions, saves, follows, memberships and notifications resolve to existing records and correct recipients.
- [ ] A new session / second browser sees the populated feed; records survive API restart.
- [ ] Two distinct owners cannot read private drafts, saves or scoped memory through each other's session.
- [ ] **No simulated content** is silently treated as authentic organic community engagement or as a confirmed memory fact.
- [ ] Posting and community permissions, pagination and mobile layout are verified end-to-end.
- [ ] `--dry-run` writes nothing, rerun doubles nothing, `--reset-demo` deletes nothing outside the demo namespace.
- [ ] One harmless false-positive and one spam fixture reach review flow; no model auto-bans an account.
- [ ] Runner records actual tests, screenshots/URLs where applicable and remaining blockers; no fabricated pass statuses.
