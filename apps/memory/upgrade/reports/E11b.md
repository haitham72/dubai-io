## B1 — lazy embedding of older facts (`apps/memory`)

`core/embed.py` rewritten around three pieces:

- `embed_query` / `embed_passages` **never load or download the model** on the
  request path: they raise `RuntimeError` when no session is loaded. The E9d
  `/v1/admin/warmup` endpoint (`api/app.py`) now calls `is_available()` +
  `embed_query("warm-up")` to load it; `start-all.ps1` already calls warmup
  after the API is healthy. Until then the semantic channel honestly reports
  `embedder_unavailable`.
- **Failed loads are cached**: `_LOAD_RETRY_AT` + `TM_EMBED_LOAD_BACKOFF_S`
  (default 60 s) means an offline query path makes one download attempt per
  backoff window, not one per call.
- `ensure_embeddings` keeps going until done: per-owner `_PENDING` queue fed by
  `_select_pending` (the expensive NOT-EXISTS + ORDER BY scan runs once per
  `batch_size * _LAZY_FETCH_FACTOR` rows, not once per sweep), `_embed_rows`
  embeds within `TM_SEMANTIC_LAZY_BUDGET_S` (default 0.04 s ≈ one batch of 8),
  sweeps paced to one per `TM_SEMANTIC_LAZY_INTERVAL_S` (default 5 s) per owner,
  and `facts_version` is marked done in `_BACKFILLED_AT` only when a sweep
  finds the queue drained AND the select returned a short page. Erased /
  history / quarantine / forget-rule exclusions unchanged (same SQL, extracted
  verbatim into `_select_pending`). `embed_pending_facts` keeps its signature
  and stats dict for the worker path (`queue/worker.py` unchanged).
- `core/applier.py` calls `ensure_embeddings(database, owner, once_per_version=False)`
  (old `limit=200` kwarg removed); `acceptance/s10_hybrid_ablation.py` warmup
  updated to `is_available()` + `embed_query("warm-up")`.

**Latency note:** the first cut (full pending SELECT + embed every 2 s) regressed
the 20k p95 gate to ~290–900 ms. The pending scan alone costs ~180–200 ms at
20k facts, so it is now amortized through the per-owner queue and each sweep is
capped at ~one embed batch; the gate passes again (see below).

Tests: `tests/test_embed_lazy_backfill.py` (new, 4 tests): 150 facts drain to
`embedding IS NOT NULL` with the version marked done only at the end; unloaded
model → `embedder_unavailable` and `embed_query` raises instead of downloading;
failed load cached for the backoff window (1 attempt, then 1 more after expiry);
`embed_pending_facts` time budget reports `fetched`/`remaining`.

## B2 — pairing consume + session in one transaction (`apps/api`)

- `app/db.py`: `PostgresDB` and `SQLiteDB` wrappers gained `begin()` /
  `commit()` / `rollback()` / `close()`.
- `app/identity/store.py`: new `complete_pairing_atomic()` — `UPDATE
  cs_pairing_codes SET consumed_at … WHERE consumed_at IS NULL` first (returns
  the code's `user_id` or `None` on a lost race), then `INSERT cs_app_sessions`
  + audit row on the same connection.
- `app/identity/service.py`: `issue_user_session` split into prepare/write
  phases; `_complete_pairing` consumes the code FIRST inside one transaction,
  then writes the session — a failed consume leaves no session row; the race
  loser still gets 409 `code_already_used`.

Test: `tests/test_e2_signin_pairing.py` — new case asserts a failed consume
leaves zero rows in `cs_app_sessions`.

## B6 — `stop-all` PID-reuse check (`scripts/dev`)

`start-all.ps1` records each PID with process name + start time into a
sidecar `.pids.meta.json` (gitignored via `scripts/dev/.gitignore`).
`stop-all.ps1` verifies the live process's name AND start time against the
recorded meta before `taskkill`; mismatches are skipped with a warning.
No test harness exists for `scripts/dev`; verified with a standalone replica
(`%TEMP%\test_pids_logic.ps1`) covering three scenarios: matching meta →
killed; wrong start time → skipped, process left alive; wrong process name →
skipped, process left alive.
