# E7 - Receipt / order / booking pre-pass (branch e7/receipts, tip deeadb7)

## What
- New `apps/memory/src/temporal_memory/ingest/receipts.py`: pure regex pre-pass over email/gmail/notes records (EN + AR, Arabic-Indic digits, AED/USD/Dhs/درهم).
  Purchases (merchant, item, amount, currency, date, order id, incl. Amazon `NNN-NNNNNNN-NNNNNNN`), devices (brand, model, capacity, condition when stated), bookings (what, where, when; provider email only).
- Emits contract-v2 `OutFact`s: predicate buys/visits/other, object_text, event_at, span_record_id/start/end (span covers item..amount..order id), `stated=False` -> applier stores provenance `inferred` (a merchant email is never "You told me"). Merchant becomes an org entity with role `merchant`.
- Rule 9: `pre_write` runs on the record, its author and every emitted fact string; any hit (clinic, pharmacy, credential...) -> nothing emitted for that record, only `(record_id, category)` kept in `context["prefilled_held_back"]` (never text). The LLM path still sees the record and quarantines through the normal gate.
- Hooks (small): `PostgresJobs._build_bundle` adds `context["prefilled"]`; `core/extract.format_user_prompt` prepends a "PRE-FILLED SLOTS ... final, do not restate/change" section only when slots exist (system prompt and PROMPT_VERSION unchanged); `PostgresJobs.submit` merges pre-filled facts into the attempt output; `core/validator.py` step 3b drops any LLM fact that touches a pre-filled record and changes an amount / order id or restates the slot (`prefilled_slot_changed`, non-fatal fact drop).
- Outside the owned list, needed for the feature: `core/applier.py` INSERT now persists predicate, object_text, polarity, modality, event_at, span_* (columns existed since migration 0003 but the day-packet applier never wrote them). Flag for review.
- Circularity: `ingest/__init__` imports `queue.jobs`, so jobs.py and validator.py import receipts lazily.

## Tests (`tests/test_receipts.py`, 15)
iPhone receipt, Amazon.ae order, Talabat order, Arabic receipt (verbatim amount `١٢٠٫٥٠ درهم`, order id, text_orig), restaurant booking, clinic booking + pharmacy order held back, newsletter / chit-chat / amount-only rent receipt / user note emit nothing, prompt note present only when slots exist, validator rejects changed amount, wrong order id and restated slot while keeping unrelated LLM facts, Postgres applier test (typed fields + provenance inferred persisted).
Full apps/memory suite on the contest-memory venv: **428 passed, 8 skipped, 0 failed** (before E7 on this base: 413 passed + 8 skipped -> +15 new). No failures to compare against origin/main. `apps/web` diff vs baseline tag: clean.

## Cost (S2, gold month)
- Before (U7_main, 4e2646d, claude-haiku-5-5): extract $0.198221, mean $0.006394/day, p95 $0.008174, target $0.0044.
- After: **estimate, not measured.** The gold corpus is almost receipt-free: on all 242 gold email/notes records the pre-pass pre-fills **0** slots (only g085, the clinic reminder, is held back) and the prompt is byte-identical when nothing is pre-filled. So the S2 gold-month cost is unchanged by construction (~$0.0064/day); an S2 re-run would only show LLM noise, so it was not run (no Docker lock, no subscription spend).
- Effect on receipt-bearing data (estimate from the four synthetic receipts): the fact + merchant entity JSON the LLM would write is ~530 chars ~ 148 output tokens per receipt = ~$0.00074 at Haiku $5/M out; the note adds ~35 input tokens per receipt (+$0.00004) plus a ~85-token header once per day with receipts. Net about -$0.0007 per receipt, i.e. ~11% of the current mean day per receipt. The E7 target ($0.0044) cannot be reached on the gold month by this pre-pass alone; it needs receipt-heavy real mail or other levers.
